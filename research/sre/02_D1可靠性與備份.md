# D1 只有 7 天的時光機，每日匯出要自己做

> 研究日期：2026-11-02。對應 issue #12「研究題目：D1 可靠性」。標「（推論）」的段落是推論，不是查到的事實；查不到的寫「查不到」。本筆記只讀文件與 `--help`，沒有對正式 D1 做任何匯出、還原或寫入。

桶緝犯的 D1（`tongjifan`，APAC，約 78 KB，`cases`、`reports` 兩張表）在 Free 方案下，Time Travel 只能回到 **7 天內**的任一分鐘（Paid 是 30 天），而且還原會**直接覆蓋原資料庫**，目前不能還原到另一個資料庫 ([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)；[D1 Limits](https://developers.cloudflare.com/d1/platform/limits/))。所以「誤刪後 8 天才發現」或「想先看看舊資料長怎樣再決定」，都要靠自己的匯出檔。匯出有 `wrangler d1 export` 和 REST API `POST .../d1/database/{id}/export` 兩條路；beta 版 `cf` CLI（1.0.0-beta.26）**沒有匯出指令**，只有 `cf d1 time-travel restore` 與 `get-bookmark`。D1 沒有查得到的公開 SLA，Cloudflare 的 100% 可用性 SLA 只給 Business 與 Enterprise 方案 ([Cloudflare Plans FAQ](https://www.cloudflare.com/plans/faq/))。read replication 只加速讀取、寫入仍走單一 primary，對台灣使用者、APAC 主庫、每天幾百筆的量沒有幫助。建議做法是：GitHub Actions 每天用 REST API 匯出一次、加密後存成 artifact（公開 repo 最多留 90 天），每季在本機 D1 與一個演練用資料庫各還原一次。成本 0 元，第一次建置約半天，之後每季約 30 分鐘。

```
 時間軸（今天往回）         還原工具                       粒度
 ─────────────────────────────────────────────────────────────────
 0 ── 7 天                   Time Travel（內建，覆蓋原庫）   任一分鐘
 0 ── 90 天                  每日匯出 artifact（要自建）     每天一份
 90 天以前                   沒有（除非另外存到 R2／私人 repo）
```

## Time Travel：Free 7 天、Paid 30 天，還原是原地覆蓋

**結論**：Time Travel 不用開、不收費，但 Free 只有 7 天，還原會覆蓋整個資料庫並中斷進行中的查詢；目前不能還原成另一個資料庫，所以不能「先還原到旁邊看看」。

**依據**：

- 保留天數：Limits 表寫「30 days (Workers Paid) / 7 days (Free)」，同一張表也限制「10 restores per 10 minutes (per database)」([D1 Limits](https://developers.cloudflare.com/d1/platform/limits/))。Time Travel 頁的說明一致 ([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/))。
- 永遠開啟、不另外收費：「You do not need to enable Time Travel. It is always on.」「Database history and restoring a database incur no additional costs.」([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/))
- 會覆蓋：文件的 Caution 寫「Restoring a database to a specific point-in-time is a *destructive* operation, and overwrites the database in place.」執行中的查詢會被取消並回錯誤 ([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/))。
- 可以反悔：還原後會回傳「還原前」的 bookmark，再還原到那個 bookmark 就能復原；還原到某個 bookmark 不會刪掉較舊的 bookmark ([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/))。
- 不能還原到別的資料庫：「Time Travel does not yet allow you to clone or fork an existing database to a new copy.」([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/))
- 時間戳與 bookmark 的換算是固定的：同一個時間戳永遠對應同一個 bookmark ([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/))。

**指令對照**（只列出，不執行；`<DB_ID>` 是 `backend/cloudflare.config.ts` 裡的 D1 UUID）：

| 動作 | wrangler（4.71.0） | `cf`（1.0.0-beta.26） |
|---|---|---|
| 取得目前或某時間點的 bookmark | `wrangler d1 time-travel info tongjifan [--timestamp=2026-11-01T12:00:00+08:00]` | `cf d1 time-travel get-bookmark <DB_ID>`（`--help`：可給時間戳，回傳「at or before」的最近 bookmark） |
| 還原到時間點 | `wrangler d1 time-travel restore tongjifan --timestamp=<unix 或 RFC3339>` | `cf d1 time-travel restore <DB_ID> --timestamp <ISO 8601>` |
| 還原到 bookmark | `wrangler d1 time-travel restore tongjifan --bookmark=<bookmark>` | `cf d1 time-travel restore <DB_ID> --bookmark <bookmark>` |
| 先演練不執行 | 無 | `cf d1 time-travel restore ... --dry-run`（`--help`：「Validate and show what would happen without executing」） |
| 跳過確認 | wrangler 會互動式問 y/N | `-f, --force` |

`cf` 只接受資料庫 UUID，不接受名稱（`cf d1 migrations apply --help` 寫明「names and binding names are not accepted」；time-travel 指令的位置參數也是 `<database-id>`）。wrangler 的 `--timestamp` 說明寫「within the last 30 days」，但那是 Paid 的上限，Free 實際只能回到 7 天（推論，依 Limits 表）。

## 匯出：wrangler 有、`cf` 沒有，REST API 可以從 GitHub Actions 排程

**結論**：每日備份要用 `wrangler d1 export --remote` 或直接打 REST API。`cf` 目前查不到匯出指令。REST API 是「先發起、再輪詢、最後拿簽名網址下載」的流程，用 `curl` 就能在 GitHub Actions 裡做完，不需要安裝 wrangler。

**依據**：

- `cf` 沒有匯出：用 `bunx cf cli search "export a D1 database to SQL file"`、`"export database as SQL dump"` 搜尋，結果只有 `cf d1 query`、`cf d1 raw`、`cf d1 migrations apply` 等；`cf d1 --help` 列出的子指令是 `create / delete / edit / get / list / migrations / query / raw / time-travel / undelete / update`，沒有 export。用 `cf d1 query` 自己 `SELECT *` 再拼 SQL 是可行的替代（推論），但要自己處理 schema 與跳脫，不建議。
- wrangler 匯出：`npx wrangler d1 export <database_name> --remote --output=./database.sql`，另有 `--table`、`--no-data`、`--no-schema` ([Import and export data](https://developers.cloudflare.com/d1/best-practices/import-export-data/))；本機 `bunx wrangler d1 export --help`（4.71.0）的選項相同。
- 匯出的限制：不支援虛擬表（FTS5）；「A running export will block other database requests.」([Import and export data](https://developers.cloudflare.com/d1/best-practices/import-export-data/))。我們沒有虛擬表；78 KB 的匯出擋住的時間應該很短（推論），但仍排在離峰。
- REST API：`POST /accounts/{account_id}/d1/database/{database_id}/export`，body `{"output_format":"polling"}`，之後帶 `current_bookmark` 繼續輪詢，完成時回傳 `result.signed_url` 與 `filename`；可用 `dump_options.tables / no_data / no_schema`。文件警告匯出期間「your D1 will be unavailable to serve queries」，且「an in-progress export must be continually polled or will automatically cancel」([API：Export D1 Database as SQL](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/))。
- 官方範例用的就是這支 API：Workflows 每天 `0 0 * * *` 觸發，發起匯出、輪詢到 `signed_url`、串流存進 R2；token 要有「permission to export the target D1 database」([Export and save D1 database](https://developers.cloudflare.com/workflows/examples/backup-d1/))。API token 的確切權限名稱（D1 Read 還是 D1 Edit）在 API 頁**查不到**；因為是 POST，先用 D1 Edit 試（推論）。
- 還原匯出檔：`wrangler d1 execute <db> --remote --file=backup.sql`，單檔上限 5 GB ([Import and export data](https://developers.cloudflare.com/d1/best-practices/import-export-data/))；本機驗證用 `--local`。

GitHub Actions 版的流程大致如下（推論，沒有實跑）：

```sh
API=https://api.cloudflare.com/client/v4/accounts/$CF_ACCOUNT_ID/d1/database/$D1_ID/export
BM=$(curl -s -X POST $API -H "Authorization: Bearer $CF_TOKEN" --json '{"output_format":"polling"}' | jq -r .result.at_bookmark)
for i in $(seq 1 30); do
  R=$(curl -s -X POST $API -H "Authorization: Bearer $CF_TOKEN" --json "{\"output_format\":\"polling\",\"current_bookmark\":\"$BM\"}")
  URL=$(echo "$R" | jq -r '.result.signed_url // empty'); [ -n "$URL" ] && break; sleep 2
done
curl -s "$URL" -o tongjifan-$(date -u +%F).sql
```

## 單一區域：寫入只有一個 primary，沒有查得到的 SLA

**結論**：D1 每個資料庫只有一個 primary 在一個地點服務讀寫；資料會持久化到多個地點，但服務本身是單點。D1 沒有公開 SLA，Free 方案也沒有任何 SLA。對單人維運的示範專案，這是可接受的風險，重點放在「壞了能知道」（見 03）與「資料救得回來」（本篇）。

**依據**：

- 單一 primary：沒開 read replication 時，「D1 routes all queries (both read and write) to a specific database instance in one location in the world」([Global read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/))；每個 D1 資料庫背後是一個 Durable Object，「inherently single-threaded」([D1 Limits](https://developers.cloudflare.com/d1/platform/limits/))。
- 寫入持久化到多處：「Writes need to be durably persisted across several locations」([D1 Limits](https://developers.cloudflare.com/d1/platform/limits/))。
- 位置：預設建在建立請求附近，可以給 location hint 但「does not guarantee」；jurisdiction 只能建立時設定 ([Data location](https://developers.cloudflare.com/d1/configuration/data-location/))。
- SLA：Cloudflare 的 SLA 只給 Business（100% uptime guarantee、以服務抵免補償）與 Enterprise ([Cloudflare Plans FAQ](https://www.cloudflare.com/plans/faq/))。D1 專屬的 SLA **查不到**；`cf docs search "D1 service level agreement uptime"` 只找到 Time Travel、除錯、資料安全等頁面。
- Free 的額度用完就停：Free 每天 500 萬 rows read、10 萬 rows written，超過後「you will not be able to run queries against D1」，直到 00:00 UTC（台灣 08:00）重置 ([D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))。對我們來說，**額度用完比 D1 機房故障更可能發生**（推論，見下一節與 04）。

## read replication：不適合我們

**結論**：不要開。它只讓遠方使用者讀得快，寫入照樣送到 primary；我們的使用者在台灣、primary 在 APAC，資料只有幾百列，而且要改用 Sessions API 才會生效。

**依據**：

- 必須改程式：「To use read replication, you must use the D1 Sessions API, otherwise all queries will continue to be executed only by the primary database.」([Global read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/))
- 寫入不變：「All write queries are still forwarded to the primary database instance. Read replication only improves the response time for read query requests.」副本是非同步複製，可能「arbitrarily out of date」([Global read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/))。
- 不另收費，但照樣計 rows read／written ([D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))，所以也解不了 Free 額度問題。
- 關閉要最多 24 小時才生效 ([Global read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/))。
- primary 故障時副本能不能繼續服務讀取：**查不到**。文件只講延遲與吞吐，沒有把 read replication 定位成高可用方案。

## 每日備份：GitHub Actions 比 Worker Cron＋R2 適合單人 Free 方案

**結論**：選 GitHub Actions。它不用在 Cloudflare 多開資源、不用 R2 訂閱、設定進版控；缺點是公開 repo 的 artifact 任何人都能下載、最多留 90 天、排程可能延遲，60 天沒動靜還會被停用。Worker Cron／Workflows 寫 R2 在 Free 也做得到，但要先在 R2 完成訂閱 checkout，還要多維護一個 Worker。

| 項目 | A. GitHub Actions 排程 | B. Worker Cron／Workflows 寫 R2 |
|---|---|---|
| 費用 | 公開 repo 的標準 runner 免費 ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)) | R2 免費額度 10 GB-月、Class A 每月 100 萬次 ([R2 Pricing](https://developers.cloudflare.com/r2/pricing/))；但要先「add an R2 subscription」([R2 Get started](https://developers.cloudflare.com/r2/get-started/))，是否需要綁卡**查不到**明文 |
| 用量 | 每天 1 次，約 1 分鐘 | Cron：Free 每帳號 5 個、每次 10 ms CPU（等網路不算）([Workers Limits](https://developers.cloudflare.com/workers/platform/limits/))；Workflows：Free 每天 3,000 steps、1 GB-月儲存 ([Workflows Pricing](https://developers.cloudflare.com/workflows/reference/pricing/)) |
| 保留 | 公開 repo 的 artifact 最多 90 天 ([Store and share data](https://docs.github.com/en/actions/tutorials/store-and-share-data)) | 自己決定，可永久 |
| 可見性 | 下載 artifact 需要 repo 的讀取權限 ([Download workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts))，公開 repo 等於任何人都有（推論）→ **要先加密** | 私有 bucket |
| 可靠度 | 排程可能延遲，負載高時「some queued jobs may be dropped」；公開 repo 60 天沒有活動會自動停用 ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)) | Cron 以 UTC 執行，變更最多 15 分鐘才生效 ([Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)) |
| 憑證 | Repo secret 放 Cloudflare API token | Worker secret 放 API token（範例要求）([Export and save D1 database](https://developers.cloudflare.com/workflows/examples/backup-d1/)) |
| 額外維護 | 一個 workflow 檔 | 一個新 Worker＋R2 bucket＋部署流程 |

容量算式：78 KB × 90 份 ≈ 7 MB，量級很小。就算一年後資料長到 10 倍，780 KB × 90 ≈ 70 MB，仍遠低於任何上限（推論）。

資料敏感度：`cases` 只有桶編號、狀態、隊名、時間；`reports` 只有來源、類型、時間（`backend/migrations/0001_init.sql`），沒有個資。即使如此，正式資料不該公開，所以 artifact 還是用 `age` 或 `gpg --symmetric` 加密，金鑰放 repo secret，另外存一份在 Jin 的密碼管理器（推論）。

**還原演練（每季一次，約 30 分鐘）**：

1. **匯出檔演練（零風險）**：下載最近一份 artifact、解密，`wrangler d1 execute tongjifan --local --persist-to /tmp/drill --file=backup.sql`，比對 `SELECT COUNT(*) FROM cases`、`reports` 與匯出當時記錄的筆數。匯出 job 可順便用 `cf d1 query` 抓筆數寫進 manifest（推論）。
2. **Time Travel 演練（不碰正式庫）**：開一個演練用資料庫（Free 可建 10 個 ([D1 Limits](https://developers.cloudflare.com/d1/platform/limits/))），寫幾列、記下時間、刪掉，用 `cf d1 time-travel restore <演練庫 ID> --timestamp ... --dry-run` 再正式還原，確認資料回來，最後刪掉演練庫。這一步只驗證流程與指令，因為 Time Travel 不能還原到別的庫，正式庫的還原無法事先演練。
3. 把每次演練的結果與耗時記在 issue 或 `research/sre/` 底下，作為 RTO 的實測值。

## 對桶緝犯的意義

**R5（沒有備份演練）**：

- 現況只靠 Time Travel，Free 只有 7 天，而且只能覆蓋原庫。最常見的災難是「誤操作」，例如 `cf d1 query --sql "DELETE ..."` 打錯庫，或公開的 `PATCH` 被亂改（見 04）。如果 7 天內有發現，Time Travel 救得回來；超過 7 天就沒有任何備份。
- 建議：
  1. 新增 `.github/workflows/d1-backup.yml`：每天 UTC 19:17 跑（台灣 03:17，避開整點延遲），打 REST API 匯出、加密後上傳 artifact，`retention-days: 90`；另外加 `workflow_dispatch` 方便手動跑。
  2. 失敗時通知：job 失敗會寄 Email 給 Jin（GitHub 預設行為，推論），或在最後一步打 Discord webhook。
  3. 60 天停用的問題：單人維運可能兩個月沒 commit。被停用的 workflow 不會自己醒來，要在 60 天內製造 repo 活動：例如用 keepalive 類 action 定期自動 commit ([keepalive-workflow](https://github.com/MikasaEureka/keepalive-workflow))，或在行事曆每 50 天提醒自己看一次 Actions 頁（推論）。03 的探測 workflow 有同樣問題，一起處理。
  4. 每季依上節做兩種演練；在 CLAUDE.md 的「部署」段補一行「正式 D1 還原只由 Jin 執行，先 `--dry-run`」。
- 成本：0 元（公開 repo 的 Actions 免費、Time Travel 免費）。
- 工作量：建置約 0.5 天（API token、secret、workflow、加密、第一次演練）；之後每季約 30 分鐘。

**R4／額度（與 02 相關的部分）**：

- Free 的 D1 額度用完會整天無法查詢，到台灣 08:00 才重置 ([D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))。issue R2 算過，一個管理端分頁一天就可能讀掉 2,100 萬 rows（43,200 次 × 約 500 列），是 500 萬上限的 4 倍以上。所以「可靠性」的第一優先不是多區域，而是**修輪詢**（issue R2）與**限流**（04）。
- 不建議：開 read replication、為了 D1 SLA 升級 Business。前者對我們沒效果；後者每月費用遠超過這個專案的價值，而且 SLA 只是事後抵免，不會讓服務比較不容易掛（推論）。

**R7（外部依賴）**：與本篇無直接關係。D1 本身就是 Cloudflare 的依賴，本篇的結論是「接受單點，確保資料救得回來」。

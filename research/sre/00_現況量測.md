# 桶緝犯正式環境現況量測

> 量測日期：2026-11-02。資料來源是 Jin 的 Cloudflare 帳號，全部用唯讀查詢取得：`cf accounts subscriptions get`、`cf d1 get`，以及 [GraphQL Analytics API](https://developers.cloudflare.com/analytics/graphql-api/) 的 `workersInvocationsAdaptive`、`d1AnalyticsAdaptiveGroups`、`d1QueriesAdaptiveGroups`。時間一律是 UTC。標「（推論）」的是推論。各項額度上限與單價的出處見 [01_cloudflare額度與部署能力.md](01_cloudflare額度與部署能力.md)，這份只記實測值。

帳號是 **Free 方案**，`cf accounts subscriptions get` 回傳空陣列，代表沒有 Workers Paid 訂閱。正式站從 10-27 搬進這個帳號以來，兩個 Worker 都**沒有任何錯誤**。目前的流量很小，最高的一天（11-02）後端 1,193 次請求。成本幾乎全部來自管理端輪詢的那一條「列出全部案件」查詢，它占 D1 rows read 的 99.7%，每次讀約 500–700 列（兩種算法的差異見下文）。照這個數字，**一個管理端分頁開一整天，就會讀掉 2,200 萬到 3,000 萬列**。另一個沒在 issue 裡列出的數字是後端 CPU time：每小時的 p99 最高到 8.1 ms，要拿去和 Free 方案每次請求的 CPU 上限比。

## 11-02 後端每小時延遲

wall time 是 Worker 從收到請求到回應的總時間，包含等 D1；CPU time 只算 Worker 自己的運算。GraphQL 回傳的單位是微秒，下表已換成毫秒。

| 小時（UTC） | 請求 | wall p50 | wall p99 | CPU p99 |
|---|---:|---:|---:|---:|
| 03 | 584 | 49 ms | 294 ms | 3.3 ms |
| 04 | 444 | 134 ms | 192 ms | 7.7 ms |
| 05 | 70 | 138 ms | 396 ms | 7.4 ms |
| 06 | 73 | 135 ms | 162 ms | 8.1 ms |
| 07 | 18 | 134 ms | 364 ms | 2.7 ms |

- wall time p50 約 134 ms，而 D1 查詢本身 p50 只有 1.17 ms（見下節），所以大部分時間花在 Worker 與 D1 之間的往返，不是查詢（推論）。
- 06 點有 2 次 `clientDisconnected`，是使用者在回應前就關掉連線，不算錯誤。

## D1 用量：一條查詢就占 99.7%

| 日期 | readQueries | rowsRead | writeQueries | rowsWritten |
|---|---:|---:|---:|---:|
| 10-27 | 183 | 111,163 | 438 | 1,310 |
| 10-28 | 105 | 44,101 | 53 | 159 |
| 10-29 | 223 | 125,984 | 16 | 34 |
| 11-02 | 1,398 | 599,684 | 189 | 386 |

10-27 的大量寫入是從原團隊帳號搬資料過來時的 `INSERT ... VALUES (...)`，查詢紀錄裡看得到寫死數值的 INSERT（推論：一次性匯入，之後不會再發生）。

依查詢分組，10-27 到 11-02：

| 查詢 | 次數 | rowsRead | 每次讀幾列 | D1 耗時 p50／p99 |
|---|---:|---:|---:|---|
| 列出全部案件（`GET /api/cases`） | 1,288 | 896,985 | 696 | 1.17／4.57 ms |
| 讀單一案件（`GET /api/cases/:id`） | 223 | 695 | 3.1 | 0.27／0.88 ms |
| 查案件狀態（`PATCH` 前檢查） | 370 | 370 | 1 | 0.16／0.39 ms |
| 其他所有查詢 | — | 約 1,500 | — | — |

列出全部案件的 SQL 是 `cases LEFT JOIN reports ... GROUP BY c.id ORDER BY c.id DESC`，沒有 `WHERE`。每次讀的列數約等於 `cases` 加 `reports` 的總列數再多一些：224 + 271 = 495，實測 696，多出來的部分是 JOIN 與排序的成本（推論）。它占 rows read 的比例是 896,985 ÷（896,985 + 695 + 370 + 約 1,500）≈ **99.7%**。

這兩張表的數字對不起來：查詢分組的「列出全部案件」單項 rowsRead（896,985），比每日表四天加總（111,163 + 44,101 + 125,984 + 599,684 = 880,932）還多。GraphQL 的 Adaptive 資料集會抽樣，兩個資料集各自估算，所以只能當作量級（推論）。改用 11-02 一天的比例估算，每次後端請求平均讀 599,684 ÷ 1,193 ≈ 503 列。以下估算用 **500 列當下限、696 列當上限**。

## 一個管理端分頁一天的成本

`usePoll` 每 2 秒打一次 `GET /api/cases`，分頁隱藏時也照打（`frontend/src/shared/api.ts`）。

```
一天的請求 = 86,400 秒 ÷ 2 秒 = 43,200 次（前端 Worker）
           + 43,200 次（經 service binding 的後端 Worker）
D1 rows read = 43,200 × 500～696 列 ≈ 21,600,000～30,067,200 列
```

案件與回報每多 100 筆，每次讀的列數也跟著多約 100 列以上，這個成本會繼續線性成長。和 Free 方案上限的比較、以及 service binding 是否算兩次請求，見 [01](01_cloudflare額度與部署能力.md)。

## CPU time

後端每小時 CPU p99 最高 8.1 ms（11-02 06:00），每日 p99 最高 6.7 ms。列出全部案件時要把幾百列轉成 JSON，CPU 會跟著案件數成長（推論）。

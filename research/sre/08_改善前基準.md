# 階段 2 改善前的基準

> 量測日期：2026-11-03（UTC）。階段 2 每做完一項改善，就用最後一節的指令重量一次，跟這份比。標「（推論）」的是推論。

正式站平常幾乎沒有人用：11-03 整天後端只有 43 次請求，大多是 UptimeRobot 打 `/api/health`。每日總量會隨「有沒有人開著頁面」大幅變動，拿來當基準沒有意義。所以這份記的是**單次請求的成本**和**開著一個分頁一天的成本**，改善前後都能用同樣的方法算。

## 單次請求的成本

| 項目 | 值 | 來源 |
|---|---|---|
| `cases` 列數 | 224 | `cf d1 query` 唯讀 `SELECT COUNT(*)` |
| `reports` 列數 | 271 | 同上 |
| `GET /api/cases` 每次讀幾列 | 495–718 | 下限：直接跑 COUNT 查詢回傳的 `meta.rows_read` 是 495（兩張表各掃一次）；上限：GraphQL `d1QueriesAdaptiveGroups` 的列表查詢，11-02 平均 711.4、11-03 平均 718.0 |
| `GET /api/cases` 回應大小 | 47,952 bytes，gzip 後 3,626 bytes | `curl -w '%{size_download}'` |
| `GET /api/cases/:id` 每次讀幾列 | 3 | GraphQL 與 Analytics Engine SLI 一致 |
| `GET /api/health` 每次讀幾列 | 0 | SLI；`SELECT 1` 不讀資料表 |

兩種算法差在 JOIN 與 GROUP BY 的成本，見 [00](00_現況量測.md)。D1 額度看的是 Cloudflare 自己的統計，所以規劃時用上限 718 列（推論）。

## 哪些頁面在輪詢

全部透過 `frontend/src/shared/api.ts` 的 `usePoll`，**分頁在背景時也照打**。

| 頁面 | 打什麼 | 間隔 | 什麼時候停 |
|---|---|---|---|
| `/admin` 管理端待辦 | `GET /api/cases` | 2 秒 | 不停 |
| `/status` 狀態看板 | `GET /api/cases` | 2 秒 | 不停 |
| `/map` 找桶地圖 | `GET /api/cases` | 5 秒 | 不停 |
| `/b/<桶編號>` 市民回報後的進度 | `GET /api/cases/:id` | 2 秒 | 案件完成或 404 |
| `/b/<桶編號>` 同一頁的「附近桶位」 | `GET /api/cases` | 2 秒 | 案件完成、404 或桶編號對不上 |

市民進度頁同時打兩條：自己的案件只讀 3 列，但附近桶位拉的是**全部案件列表**。每個掃 QR Code 回報的市民，在案件完成前都和一個管理端分頁一樣貴。

## 開著一個分頁的成本

Free 方案每日上限：Workers 請求 10 萬次、D1 rows read 500 萬列，台灣時間 08:00 歸零（[01](01_cloudflare額度與部署能力.md)）。前端經 service binding 呼叫後端，Free 方案會不會算兩次查不到，以下照 01 保守地算兩次。

```
2 秒輪詢一次 /api/cases，分頁開一整天：
  請求    86,400 秒 ÷ 2 = 43,200 次 × 2（前端＋後端）= 86,400 次 → Workers 額度的 86%
  D1 讀取 43,200 × 495～718 列 = 2,138 萬～3,102 萬列       → D1 額度的 4.3～6.2 倍

D1 讀取額度用完需要多久：
  5,000,000 ÷ 718 列 = 6,964 次 × 2 秒 ≈ 3.9 小時
  5,000,000 ÷ 495 列 = 10,101 次 × 2 秒 ≈ 5.6 小時

/map 5 秒一次：一天 17,280 次，D1 855 萬～1,241 萬列，約 9.7～14 小時用完
```

只要一個人把管理端、狀態看板或進度頁開在背景，不到半天正式站就會停擺到隔天 08:00。案件與回報每多 100 筆，每次讀的列數也跟著多 100 列以上，用完的時間會越來越短（推論）。

## 階段 2 的目標

| 改善 | 預期效果 |
|---|---|
| 輪詢只在分頁可見時跑，進度頁背景放慢到 15 秒 | 背景分頁的成本從上表降到 0（進度頁降到 1/7.5）；開在前景的成本不變 |
| ETag／304 + `meta.version` | 資料沒變時每次只讀 1 列、回應幾乎是空的；列數不再隨案件數成長 |
| 限流 + 每案回報上限 | 擋住刻意灌請求，不靠使用者自律 |
| k6 壓測 | 用實測驗證上面的額度模型 |

## 重量的方法

全部是唯讀查詢。`<ACCOUNT_ID>` 是 Cloudflare 帳號 ID，token 要有 Account Analytics: Read。

1. 列表查詢每次讀幾列：GraphQL `d1QueriesAdaptiveGroups`，依 `date`、`query` 分組，看列表查詢的 `sum.rowsRead ÷ count`。

   ```graphql
   { viewer { accounts(filter: {accountTag: "<ACCOUNT_ID>"}) {
     d1QueriesAdaptiveGroups(limit: 20, filter: {date_geq: "<日期>", date_leq: "<日期>"}, orderBy: [sum_rowsRead_DESC]) {
       count dimensions { date query } sum { rowsRead }
     }
   } } }
   ```

2. 各路由的請求數、每次讀幾列、延遲：ARCHITECTURE.md「可觀測性」的 Analytics Engine SQL 範例。
3. 回應大小：

   ```sh
   U=https://tongjifan.ccyisyourbestfriend.workers.dev
   curl -s -o /dev/null -w '%{size_download}\n' $U/api/cases
   curl -s -H 'accept-encoding: gzip' -o /dev/null -w '%{size_download}\n' $U/api/cases
   ```

4. 輪詢行為：開一個管理端分頁，切到別的分頁 10 分鐘，再用第 2 步的 SQL 看這 10 分鐘的 `GET /api/cases` 次數。改善前約 300 次，改善後應該接近 0。

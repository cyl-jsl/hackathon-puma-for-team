# 先防額度被灌爆，再決定管理端要不要登入

> 研究日期：2026-11-02。對應 issue #12「R3 管理端 API 沒有驗證」。標「（推論）」的段落是推論，不是查到的事實；查不到的寫「查不到」。

目前最現實的威脅不是有人偷資料，而是有人用一個 curl 迴圈把 **Free 的每日額度灌爆**，讓整站的 API 停到隔天台灣 08:00。Workers Free 每天 10 萬請求 ([Workers Limits](https://developers.cloudflare.com/workers/platform/limits/))，換算 100,000 ÷ 86,400 秒 ≈ 每秒 1.16 次，一台筆電就做得到。D1 Free 每天 10 萬 rows written ([D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))；每筆回報寫 2–4 列，2.5–5 萬次 `POST /api/reports` 就會用完（推論，算式見下）。工具方面：Workers Rate Limiting binding 已 GA，文件沒有寫方案限制，`cf/config` 也有 `bindings.rateLimit` 可以設定，是第一道防線 ([Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/))。Cloudflare Access 現在**可以直接保護 `*.workers.dev`**，也可以只保護某個路徑，不一定要自有網域；Zero Trust Free 方案 50 人、0 元 ([Workers：Cloudflare Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/)；[Zero Trust plans](https://www.cloudflare.com/plans/sase-zero-trust/))。但 Access 只看主機名稱與路徑、不看 HTTP method，而 `PATCH /api/cases/:id` 和市民輪詢用的 `GET /api/cases/:id` 是同一個路徑，要先把管理寫入搬到 `/api/admin/*` 才擋得乾淨。另外，入口站目前**刻意開放任何人試玩管理端**（`Entry.tsx`：「任何人都能操作」），所以加登入是產品決策，不只是技術問題。建議分兩階段：現在先做限流、每案回報上限、共享 token 保護 `PATCH`／`source=sensor`，0 元、約 1 天；真的有清潔隊使用時，再用 Access 保護 `/admin*` 與 `/api/admin/*`，並把試玩改成獨立的示範資料。

```
 路由                    誰在用                      建議（第一階段 → 第二階段）
 ────────────────────────────────────────────────────────────────────────────
 GET  /、/b/*、/map、/trash  市民（掃 QR，不登入）   公開（靜態檔，不計請求）
 POST /api/reports source=citizen  市民              公開＋限流＋每案回報上限
 POST /api/reports source=sensor   感測器／模擬鈕    共享 token → 感測器用 token、模擬改走 /api/admin
 GET  /api/cases、/api/cases/:id   市民進度、地圖    公開（唯讀）；修輪詢見 issue R2
 PATCH /api/cases/:id              管理端指派／結案  共享 token → 搬到 /api/admin/*＋Access
 /admin、/status、/bins            管理端頁面        試玩期公開 → Access
 DELETE /api/cases                 本機開發          已限 localhost，維持
```

## 現況：誰能做什麼、要花多少代價

**結論**：任何人都能把案件改成「已完成」、偽造感測器通報，也能用合法請求耗盡每日額度；這些請求都回 200／201，Workers Issues 看不到（見 03）。

**依據**：

- 路由與檢查：`backend/src/index.ts` 的 `createReport` 只驗 `bin_id`（1 到 661）、`source`、`kind`；`updateCase` 只檢查狀態單向前進；沒有任何身分檢查。`DELETE /api/cases` 限 `localhost`。後端 Worker 設了 `workersDev: false`，只能經由前端 Worker 的 service binding 進來（`backend/cloudflare.config.ts`），前端 Worker 把 `/api/*` 原封不動轉過去（`frontend/worker/index.ts`）。
- 每筆回報寫幾列（推論）：新案件會寫 `cases` 1 列＋索引 `cases_bin_status` 1 列，再寫 `reports` 1 列＋索引 `reports_case` 1 列，共 4 列；合併進既有案件時只寫 `reports` 的 2 列。依據是「Indexes will add an additional written row when writes include the indexed column」([D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))。所以 100,000 ÷ 4 = 25,000 次，或 100,000 ÷ 2 = 50,000 次，就會用完 D1 的每日寫入。
- 撞到上限後：Workers 回 Error 1027 ([Workers Limits](https://developers.cloudflare.com/workers/platform/limits/))；D1「will not be able to run queries」，到 00:00 UTC 重置 ([D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))。靜態檔「free and unlimited」([Workers Pricing](https://developers.cloudflare.com/workers/platform/pricing/))，所以頁面打得開，但回報與進度全部失敗（推論）。
- Service binding 不重複計費：「Requests made from your Worker to another worker via a Service Binding do not incur additional request fees.」([Workers Pricing](https://developers.cloudflare.com/workers/platform/pricing/))

## Workers Rate Limiting binding：可用、免費，但只是近似值

**結論**：可以用來擋「單一來源灌爆」，不能當精確計數。每個 Cloudflare 機房各自計算，週期只能是 10 秒或 60 秒。

**依據**：

- 已 GA：「The `ratelimit` binding is now stable and recommended for all production workloads.」([Rate Limiting GA changelog](https://developers.cloudflare.com/changelog/post/2025-09-19-ratelimit-workers-ga/))
- 方案與費用：binding 文件與 Workers 價格頁都沒有寫方案限制或額外費用（[Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)；[Workers Pricing](https://developers.cloudflare.com/workers/platform/pricing/)）。「Free 可用」**查不到**明文（推論：可用且不另收費）。上線前先在本機與正式各試一次。
- 設定：`simple.limit` 是門檻；`simple.period`「Must be either `10` or `60`」；同一個 `namespace_id` 跨 Worker 共用計數 ([Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/))。
- 準確度：「Rate limits are approximate and apply separately in each Cloudflare location」；計數是最終一致，可能超過門檻 ([Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/))。
- key 的選擇：官方建議用使用者 ID 或 API key，「It is not recommended to use IP addresses」，因為很多人可能共用 IP ([Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/))。市民匿名回報沒有使用者 ID，只能用 IP（`cf-connecting-ip`）加 `bin_id`，門檻放寬，例如每 60 秒 10 次（推論）。行動網路的 CGNAT 會讓很多人共用 IP，所以門檻不能太低。
- `cf` 設定：beta `cf` 套件把 wrangler 的 `ratelimits` 轉成 `bindings.rateLimit`，欄位是 `namespace` 與 `simple`（從 `cf` 套件的 wrangler 轉換程式碼看到，推論：寫法是 `bindings.rateLimit({ namespace: "1001", simple: { limit: 10, period: 60 } })`）。
- 有自有網域後的替代：WAF Rate limiting rules 在 Free zone 只有 1 條、只能看 Path、只能以 IP 計數、週期 10 秒 ([Rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/))，好處是在 Worker 執行前就擋掉、不計 Worker 請求（推論）。`*.workers.dev` 不能用。

**限流擋不住分散來源**，所以要在應用層再加一個**每案回報上限**（推論）：同一個未結案件最多記 20 筆回報，超過就回 200 但不寫入。結案要靠 `PATCH`，而 `PATCH` 會被保護，所以最壞情況的寫入量是 661 桶 ×（新案 2 列＋20 筆 × 2 列）= 661 × 42 = 27,762 列，低於每日 10 萬列。這個上限不只限一天，因為案件不結案就不會重開。

## Cloudflare Access：`*.workers.dev` 可以用，路徑也可以，但不分 method

**結論**：不需要自有網域。可以保護整個 Worker，也可以用 self-hosted application 只保護 `tongjifan.ccyisyourbestfriend.workers.dev/admin` 這類路徑。Zero Trust Free 50 人，對「Jin＋幾位清潔隊窗口」足夠。限制有三個：Access 不分 HTTP method；有 static assets 的 Worker 拿不到 `ctx.access`；service binding 不會傳遞身分。

**依據**：

- 支援 `workers.dev`：一鍵開啟 Access「for your `workers.dev` and Preview URLs」([One-click Access changelog](https://developers.cloudflare.com/changelog/post/2025-10-03-one-click-access-for-workers/))。2026-08 起還能以 Worker 為單位保護全部網域 ([Workers Access changelog](https://developers.cloudflare.com/changelog/post/2026-08-14-workers-access/))。
- 只保護路徑：「Use hostname-based Access when only a specific URL… such as a `workers.dev` hostname, a Custom Domain, a subdomain, or a path」，在 Zero Trust > Access > Applications 建 self-hosted application ([Workers：Cloudflare Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/))。
- 路徑規則：`example.com/alpha/*` 涵蓋 `/alpha/one`，但**不涵蓋** `/alpha` 本身；比較具體的規則優先；不支援 query string ([Application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/))。所以 `/admin` 與 `/admin/*` 要分別列。這份文件只有主機名稱與路徑欄位，沒有 method（推論：無法只擋 `PATCH`）。
- 「Protect one Worker」會保護整個 Worker 的所有網域 ([Workers：Cloudflare Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/))。這會擋到市民，不能用在前端 Worker。
- 身分怎麼傳到程式：Access 驗證過的請求可以讀 `ctx.access`，但「Workers with Static Assets execute behind an internal router Worker… the router does not pass `ctx.access` to the user Worker」，而且「Cloudflare Access does not propagate `ctx.access` through Service Binding」([Workers：Cloudflare Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/))。我們兩個條件都中，所以要在前端 Worker 驗證 `Cf-Access-Jwt-Assertion` header 裡的 JWT（官方範例用 `jose`）([One-click Access changelog](https://developers.cloudflare.com/changelog/post/2025-10-03-one-click-access-for-workers/))，再把結果傳給後端。這個 header 經過 assets router 時會不會保留：**查不到**（推論：會，它是一般請求 header）。
- 方案：Zero Trust Free「Teams under 50 users」「$0 forever」，Access log 保留最多 24 小時 ([Zero Trust plans](https://www.cloudflare.com/plans/sase-zero-trust/))。使用者登入一次就佔一個 seat，直到被移除；service token 不佔 seat ([Seat management](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/))。建立 Zero Trust 組織時要不要綁付款方式：**查不到**官方說法。

**只保護管理端的設定（推論，依上述文件組合）**：

1. API 合約 PR：把 `PATCH /api/cases/:id` 搬到 `PATCH /api/admin/cases/:id`；「模擬感測器」改呼叫 `POST /api/admin/simulate`。`frontend/src/shared/api.ts` 與 ARCHITECTURE.md 的 API 表放在同一個 PR，先合併。
2. Zero Trust > Access > Applications > Self-hosted，網域 `tongjifan.ccyisyourbestfriend.workers.dev`，路徑列 `admin`、`admin/*`、`status`、`bins`、`api/admin/*`；policy 用 Email（Jin 與清潔隊窗口）。
3. 前端 Worker：`/api/admin/*` 先驗 JWT（`aud` 放 Worker 變數），失敗回 403；成功才轉給後端，並刪掉外部帶進來的身分 header，避免偽造。
4. 後端：`/api/admin/*` 只接受前端 Worker 加上的內部 header（後端沒有公開網址，只能從 service binding 進來）。
5. SPA 的 JS bundle（`/assets/*`）仍然公開。管理端程式碼本來就在公開 repo，這不是問題。

## Turnstile：免費、不限次數，但對我們幫助有限

**結論**：可以加在市民回報表單上擋機器人，但它擋不了真人手動洗、會增加延遲與一個外部依賴，感測器也無法使用。等到觀察到真正的機器人濫用再加。

**依據**：

- 免費版：最多 20 個 widget、「Unlimited challenges」、每個 widget 10 個 hostname、分析保留 7 天 ([Turnstile plans](https://developers.cloudflare.com/turnstile/plans/))。`*.workers.dev` 能不能當 widget hostname：**查不到**限制。
- 整合成本：前端放 widget 拿 token；後端每次回報都要呼叫 Siteverify 驗證。token 有效 300 秒、只能驗一次，過期回 `timeout-or-duplicate` ([Server-side validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/))。市民在回報頁停超過 5 分鐘才送出，就要重拿 token，要處理這個 UX（推論）。
- Siteverify 是從 Worker 發出的 subrequest，Free 每次請求可以有 50 個 subrequest ([Workers Limits](https://developers.cloudflare.com/workers/platform/limits/))，夠用；延遲增加多少**查不到**官方數字。

## 簡單共享 token：最快、最便宜，但只是門閂

**結論**：第一階段用它保護 `PATCH` 與 `source=sensor`。做法是後端放一個 Worker secret，管理端第一次開啟時輸入、存在 `localStorage`，請求帶 `Authorization: Bearer <token>`。

**缺點**（推論）：

- 所有人共用一把，無法知道誰結的案，也無法只撤銷某一個人；外洩只能整把換掉。
- 存在 `localStorage`，XSS 就能偷走；目前前端沒有使用者輸入的 HTML，風險低。
- 試玩期如果把 token 公開給訪客，就等於沒保護。所以要先決定試玩怎麼做（見下節）。
- 好處：不用 Zero Trust、不用改路徑、半天內完成；之後換成 Access 時，token 檢查可以保留給感測器用（Access 也有 service token，但感測器韌體能不能帶自訂 header 要看硬體，推論）。

## 對桶緝犯的意義

**R3（無驗證）**：

先做產品決策。入口站現在請訪客「任何人都能操作」管理端（`frontend/src/entry/Entry.tsx`），所以「加登入」會打斷試玩。建議把**示範**和**正式**分開：

- **第一階段（現在，示範期）**：目標是「不會被灌爆、資料不會被亂改到無法收拾」。
  1. 前端 Worker 對 `POST /api/reports` 與 `PATCH` 加 rate limit binding：key 用 `IP + 路由`，每 60 秒 10 次（約 2 小時）。
  2. 後端加每案回報上限 20 筆（約 1 小時），最壞寫入量壓在 27,762 列／天。
  3. 試玩照樣開放，但每天由 GitHub Actions 或 Cron 清理示範資料，或把試玩限定在幾個試玩桶（約半天，要和隊友討論）。
  4. 搭配 02 的每日備份與 03 的額度預警，被亂改時至少能還原、被灌時至少會知道。
  - 成本 0 元；工作量約 1 天，需要 Jin 部署一次。
- **第二階段（有清潔隊實際使用時）**：
  1. API 合約 PR：管理寫入搬到 `/api/admin/*`（約 2 小時）。
  2. Access self-hosted app 保護 `/admin`、`/admin/*`、`/status`、`/bins`、`/api/admin/*`；前端 Worker 驗 JWT（約半天）。
  3. 感測器用共享 token 或 Access service token 打 `POST /api/reports source=sensor`；`source=citizen` 維持公開。
  4. 試玩改用另一個 Worker 或另一個 D1，跟正式資料隔開（約 1 天，看做法）。
  - 成本：Zero Trust Free 50 人以內 0 元；超過 50 人要改 Pay-as-you-go，每人每月 7 美元 ([Zero Trust plans](https://www.cloudflare.com/plans/sase-zero-trust/))。工作量約 2 天。
- **維持公開**：`/`、`/entry`、`/b/<id>`、`/map`、`/trash`、`GET /api/cases`、`GET /api/cases/:id`、`POST /api/reports`（citizen）。市民掃 QR 不能要求登入。
- **暫不做**：Turnstile（等真的看到機器人再加）；買網域只為了 WAF 限流（Free zone 只有 1 條、10 秒週期，Worker 內的 binding 已經夠用）。買網域的主要理由是 issue R1 的 QR Code 網址，不是防濫用。

**R4（無監控）**：濫用請求是合法的 200／201，Issues 不會告警。要靠 03 的「額度預警」：每天看 Workers 請求數與 D1 rows written，超過 70% 就發 Discord。限流被觸發時（回 429），後端可以 `console.warn` 一筆，事後在 Workers Logs 查得到（推論）。

**R5（無備份演練）**：`PATCH` 被亂改屬於「資料還在、狀態錯了」，Time Travel 7 天內可以整庫還原，但會連同之後的正常資料一起倒回去（見 02）。所以第一階段的限流與回報上限，比還原能力更重要。

**R7（外部依賴）**：Access 與 Turnstile 都是新的外部依賴。Access 故障時管理端進不去，市民端不受影響（只保護管理路徑）。Turnstile 故障時市民無法回報，這是暫緩 Turnstile 的另一個理由（推論）。

# 自有網域與 QR 網址：買一個不在 Cloudflare 註冊的 .tw，舊網址由同一個 Worker 轉址

> 研究日期：2026-11-02。價格均註明幣別與查詢來源日期。標「（推論）」的是推論，不是查到的事實；查不到的寫「查不到」。本筆記只做研究，沒有購買網域，也沒有部署。

**結論**：已印出的 QR Code 指向 `tongjifan.ccyisyourbestfriend.workers.dev`。這個網址的存續綁在三件事上：Jin 的 Cloudflare 帳號、帳號子網域 `ccyisyourbestfriend`、Worker 名稱 `tongjifan`。三者任一改變，貼紙就失效。而且 `workers.dev` 不是 Jin 自己的 zone，沒辦法在 Worker 以外的地方設定轉址。

建議如下：

- **買網域**：在台灣註冊商買一個 `.tw`。PChome 新申請 NT$800、續約 NT$720/年；Gandi 是 TWD 744/年。Cloudflare Registrar 不賣 `.tw`。
- **接到 Cloudflare**：把 NS 指到 Cloudflare Free zone，再設成 Workers Custom Domain。
- **轉址**：在前端 Worker 依 Host 判斷，對 `workers.dev` 的頁面請求回 301，`/api/*` 不轉址、照常服務。
- **舊網址**：`workers.dev` 網址要**永久保留**，不能關。
- **新貼紙**：之後印的一律用新網域，路徑維持 `/b/<桶編號>`。

整體成本是每年約 NT$720–800，工作量約 1 個工作天。

## Custom Domain 與 Route：桶緝犯要用 Custom Domain，而且網域一定要是 Cloudflare zone

**結論**：

- 兩種方式都要求網域是**同一個帳號底下、啟用中的 Cloudflare zone**。
- 桶緝犯的 Worker 本身就是 origin，該用 Custom Domain。Cloudflare 會自動建立 DNS 紀錄並發憑證。
- Route 適合「Worker 擋在另一台 origin 前面」的情況，桶緝犯用不到。

**依據**：

| | Custom Domain | Route |
|---|---|---|
| 用途 | Worker 就是 origin ([Routing](https://developers.cloudflare.com/workers/configuration/routing/)) | Worker 在既有 origin 前面當 proxy ([Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/)) |
| 前提 | 「An active Cloudflare zone」；該主機名稱不能已有 CNAME，也不能是別人的 zone ([Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)) | 啟用中的 zone，並且要自己先建一筆 proxied（橘雲）DNS 紀錄 |
| DNS／憑證 | 自動建立 DNS 紀錄，並發 Advanced Certificate（包括多層子網域） | 自己建 DNS；憑證由 Universal SSL 處理，只涵蓋一層子網域 |
| 比對方式 | 主機名稱完全相符，不支援萬用字元，不看路徑 | URL pattern，例如 `example.tw/b/*` |
| 同 zone 內 `fetch()` | 可以被同 zone 的其他 Worker 呼叫 | 不行 |

**設定步驟**（Custom Domain）：

1. 在註冊商買網域，把 NS 改成 Cloudflare 指定的兩組。
2. 在 Cloudflare 把網域加成 Free zone，等狀態變成 Active。
3. 到 Workers & Pages → `tongjifan` → Settings → Domains & Routes → Add → Custom Domain，輸入例如 `example.tw`。也可以在設定檔加：

   ```json
   routes: [{ pattern: "example.tw", custom_domain: true }]
   ```

   ([Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/#set-up-a-custom-domain-in-your-wrangler-configuration-file))
4. 處理 `www`。Custom Domain 只比對完全相同的主機名稱，`www.example.tw` 要另外建一筆 proxied 的 `A 192.0.2.0`，再設一條 Redirect Rule 轉到根網域 (同頁「Redirect between www and root domain」)。

**兩個要注意的地方**：

- **`workers.dev` 可能被自動關掉**。官方文件說，如果設定檔加了 `routes` 卻沒有寫 `workers_dev`，下次部署時「the value of `workers_dev` will be inferred as `false`」([workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/#disabling-workersdev-in-the-wrangler-configuration-file))。這樣舊貼紙會立刻失效。所以加 Custom Domain 時，前端設定**一定要明寫 `workersDev: true`**。
  - 本 repo 用 `cf` 的 `cloudflare.config.ts`，`routes` 與 `workersDev` 的確切欄位名稱，這次沒有在本 worktree 查證（`node_modules` 未安裝）。後端設定裡有 `workersDev: false` 的寫法可以參考。
- **Cache API 只在 Custom Domain 上有效**。文件寫「Workers deployed to custom domains have access to functional `cache` operations」([Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/))。換到自有網域後，Worker 才能用 Cache API（推論：`workers.dev` 上的 Cache API 沒有作用）。

## 舊 workers.dev 網址轉址：在前端 Worker 裡依 Host 回 301，`/api/*` 不轉

**結論**：

- `workers.dev` 不是 Jin 的 zone，不能用 Redirect Rules，只能由 Worker 自己回 3xx。
- 現在的設定是 `runWorkerFirst: ["/api/*"]`，`/b/300` 這類頁面直接由靜態資產回 `index.html`，**根本不會經過 Worker**。所以要把需要轉址的頁面路徑也加進 `runWorkerFirst`，並加上 `ASSETS` binding，讓 Worker 在不轉址時把請求交還給靜態檔。
- `/api/*` 在兩個主機名稱上都照常轉給後端，不轉址。

**依據**：

- **現行的 Worker**：`frontend/worker/index.ts` 只有一行 `return env.API.fetch(req)`。`frontend/cloudflare.config.ts` 設了 `notFoundHandling: "single-page-application"` 與 `runWorkerFirst: ["/api/*"]`。
- **靜態資產的計費**：靜態資產請求「free and unlimited」；符合 `run_worker_first` 的請求「will always invoke your Worker script」，在 Free 方案會計入每日 100,000 次請求 ([Static Assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/))。
  - 只把 HTML 頁面路徑加進去，例如 `/`、`/b/*`、`/map`、`/trash`、`/entry`、`/admin`、`/status`、`/bins`，JS、CSS、圖片照舊免費。
  - 這樣新網域上的頁面瀏覽也會經過 Worker，每次瀏覽計 1 次請求。和每 2 秒一次的輪詢相比可以忽略（推論）。
- **POST 與狀態碼**：
  - 301 規範上不應改變 method，但「incorrectly handled by older clients to use the GET method」；308 則保證 method 與 body 不變 ([MDN 308](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/308))。
  - 不過 `/api/*` 不應該轉址。舊網址上還開著的頁面（例如管理端分頁）用相對路徑 `fetch("/api/...")`，轉址到另一個 origin 之後，就變成跨來源請求，需要 CORS 標頭。`POST` 加 `application/json` 還會觸發預檢（推論，依 Fetch 規範的 CORS 規則）。
  - 所以 `/api/*` 在兩個 host 上都直接走 service binding，只轉址 `GET`/`HEAD` 的頁面請求。只有在將來真的要停掉舊 host 上的 API 時，才用 308。
- **301 會被瀏覽器長期快取**：301 和 308 依 RFC 9110 是「heuristically cacheable」([RFC 9110 §15.4.2](https://www.rfc-editor.org/rfc/rfc9110#section-15.4.2)；[§15.4.9](https://www.rfc-editor.org/rfc/rfc9110#section-15.4.9))，瀏覽器可能長期記住。建議先用 302 觀察一週，確認新網域穩定後再改 301。
- **程式草稿**（推論，未實作）：

  ```ts
  const CANONICAL = "https://example.tw"; // 實際網域待定
  export default {
    fetch(req, env) {
      const url = new URL(req.url);
      if (url.pathname.startsWith("/api/")) return env.API.fetch(req);   // 兩個 host 都照常服務
      if (url.hostname.endsWith(".workers.dev") && (req.method === "GET" || req.method === "HEAD")) {
        return Response.redirect(CANONICAL + url.pathname + url.search, 301); // 先用 302 觀察
      }
      return env.ASSETS.fetch(req); // 需在 assets 設定 binding: "ASSETS"
    },
  } satisfies ExportedHandler<Env>;
  ```

- **另一種做法**：把 app 搬到新的 Worker（例如 `tongjifan-web`，設 `workersDev: false`，掛 Custom Domain），原本的 `tongjifan` 改成只做轉址與 `/api/*` 代理的小 Worker。好處是新網域上的頁面瀏覽不用經過 Worker；缺點是多一個 Worker 要部署與維護。單人維運，建議先用上面的單一 Worker 做法。
- **如果關掉 `workers.dev` 會怎樣**：關掉後，該 Worker 的 `workers.dev` 路由就停用 ([workers.dev：Disabling](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/#disabling-workersdev))，舊貼紙會全部失效，而且沒有任何地方可以補一個轉址。關掉後訪客會看到什麼錯誤頁、狀態碼是多少，這次**查不到**。結論是：**只要還有舊貼紙在外面，就不能關**。

## 風險：帳號子網域可以改名，但改名或帳號消失時沒有任何轉址

**結論**：

- `ccyisyourbestfriend` 是帳號層級的子網域，可以在 dashboard 改名。改名會讓帳號下**所有** Worker 的 `workers.dev` 網址一起換掉。
- 舊名稱會不會釋出給別人註冊，**查不到**。
- 帳號被終止或刪除時，`workers.dev` 網址也會跟著消失，而且沒有任何地方可以補轉址。
- 自有網域放在另一家註冊商，就能把這個風險和帳號拆開。

**依據**：

- **改名**：帳號子網域可以在 Workers & Pages 的「Change」更改；Worker 的網址格式是 `<WORKER_NAME>.<SUBDOMAIN>.workers.dev`，由 Worker 的 `name` 決定 ([workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/#configure-workersdev))。所以改 Worker 名稱也會改變網址（推論，依網址格式）。
- **改名時的提示**：wrangler v1 的原始碼裡，改名的確認文字是「Are you sure you want to permanently move your subdomain from {}.workers.dev to {}.workers.dev?」以及「It may take a few minutes for these Workers to become available again.」([wrangler subdomain.rs](https://docs.rs/wrangler/latest/src/wrangler/commands/subdomain.rs.html))。舊名稱的保留期與能否被他人取得，這次**查不到**。
- **定位**：官方把 `workers.dev`「treated as a Free website」，定位是「personal or hobby projects that aren't business-critical」，並建議正式環境用 route 或 custom domain ([Routing：What is best for me](https://developers.cloudflare.com/workers/configuration/routing/#what-is-best-for-me))。
- **帳號終止**：自助訂閱條款寫，Cloudflare 可以「at any time, with or without notice for any reason or no reason at all」終止或暫停服務（§8）；免費服務可以由 Cloudflare「in our sole discretion」終止（§2.6）([Cloudflare Self-Serve Subscription Agreement](https://www.cloudflare.com/terms/))。終止後資料何時刪除，條款本文沒有寫，**查不到**。
- **網域放在哪裡的影響**：
  - 網域在 Cloudflare Registrar：帳號出事時，網域也在同一個帳號裡，而且 NS 不能改到別處，要先轉出 ([Registrar FAQ](https://developers.cloudflare.com/registrar/faq/))。
  - 網域在 PChome 或 Gandi：Cloudflare 帳號出事時，到註冊商把 NS 改到新平台，貼紙網址就能救回來（推論）。

## 建議：QR Code 網址的設計原則與現有貼紙處理

**結論**：網址要「自己擁有、與平台無關、短、永不改」。現有貼紙不回收，靠轉址撐著，自然汰換。

**原則**（推論，整理自上面的事實）：

1. **網域是自己的，而且註冊商和託管平台分開**：網域放在台灣註冊商，DNS 和託管放在 Cloudflare。任何一方出事，另一方都還能救。
2. **主機名稱不含平台名稱**：不要用 `workers.dev`、`pages.dev`、`vercel.app` 這類網址。
3. **路徑短而且穩定**：維持 `/b/<桶編號>`。路徑越短，QR Code 的模組越少，越容易掃（推論）。桶編號已經規定不能重跑 `etl/bins.py`（見 CLAUDE.md），所以路徑對應的實體桶不會變。
4. **不帶狀態與追蹤參數**：不要放 `?utm=` 或版本號。要統計來源時，在 Worker 端記錄就好。
5. **把網址當成 API 合約**：寫進 ARCHITECTURE.md，`/b/<id>` 永遠要能用；改前端路由時，舊路徑也要保留轉址。

**現有貼紙**：

- 舊網址的轉址 Worker 要**無限期保留**。成本是 0 元：掃碼次數遠低於 Free 方案的每日請求額度（推論）。
- 開一份貼紙清單，記錄桶編號、張貼日期、網址版本，作為之後汰換的依據。
- 新印的貼紙一律用新網域；舊貼紙破損或補貼時，順便換新。
- 將來 Cloudflare 帳號真的要換，舊貼紙會失效。這是**唯一無法事後補救**的情況，所以越早換新網域，暴露在這個風險下的舊貼紙越少。

## 對桶緝犯的意義

**結論**：花約 NT$800 和 1 個工作天，就能把 R1（QR 網址綁在 `workers.dev`）降為低風險。

1. **選網域並購買**（Jin 決定，約 0.5 小時）：
   - 建議在 PChome 或 Gandi 買泛用型 `.tw`。第一年約 NT$744–800，之後每年約 NT$720–744。
   - 如果更在意價格與設定的簡便，可以改買 Cloudflare Registrar 的 `.com`，約 US$10.46/年，但要接受「網域和帳號綁在一起」。
   - 名稱越短越好，例如 `tongjifan.tw` 這類，實際能不能註冊**未查**。
2. **接到 Cloudflare**（0.5–1 小時，主要是等 NS 生效）：加 Free zone，在註冊商改 NS。
3. **PR：前端 Worker 依 Host 轉址**（約半天）：
   - `frontend/worker/index.ts` 依上面的草稿修改。
   - `cloudflare.config.ts` 加上 Custom Domain、明寫 `workersDev: true`、加 `ASSETS` binding、在 `runWorkerFirst` 加入頁面路徑。
   - ARCHITECTURE.md 寫明 `/b/<id>` 是永久合約。
   - 部署由 Jin 用 `/deploy` 執行。
4. **驗證**（約 1 小時）：
   - `curl -sI https://tongjifan.ccyisyourbestfriend.workers.dev/b/300` 應該回 302 或 301，`Location` 指向新網域。
   - 新舊兩個網址的 `/api/cases/1` 都回 200。
   - 用手機掃一張舊貼紙，確認會轉到新網域。
5. **一週後把 302 改成 301**，並把探測（見 [07_SRE方法論_單人版.md](07_SRE方法論_單人版.md)）的目標同時設成新舊兩個網址。舊網址探測失敗，代表舊貼紙失效，要列為最高優先級。
6. **持續成本**：每年約 NT$720–800 的網域費；Cloudflare 的 zone、Custom Domain、憑證在 Free 方案都是 0 元。

# Free 方案沒有 Workers 錯誤率告警，要用 Issues 加外部探測補上

> 研究日期：2026-11-02。對應 issue #12「R4 沒有監控與告警」。標「（推論）」的段落是推論，不是查到的事實；查不到的寫「查不到」。

在 Free 方案、沒有自有網域的情況下，Cloudflare 原生的告警幾乎用不上。錯誤率告警（Origin／Advanced Error Rate）與流量異常告警只給 Enterprise，而且要以 zone 為單位設定 ([Available notifications](https://developers.cloudflare.com/notifications/notification-available/)；[HTTP Traffic Alerts](https://developers.cloudflare.com/notifications/reference/traffic-alerts/))。Health Checks 在 Free 方案是 0 個 ([Health Checks](https://developers.cloudflare.com/health-checks/))。Tail Workers 只給 Paid ([Tail Workers](https://developers.cloudflare.com/workers/observability/logs/tail-workers/))。Free 能用的有三樣：Workers Logs（每天 20 萬筆、保留 3 天）([Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/))、正在 open beta 且免費的 **Workers Issues**（遇到例外或 5xx 就能透過 automation 推到 webhook）([Issues](https://developers.cloudflare.com/workers/observability/issues/))，以及所有方案都有的 Cloudflare 事故通知 ([Available notifications](https://developers.cloudflare.com/notifications/notification-available/))。但 Issues 只看得到「Worker 有執行、而且出錯」；Worker 根本沒被執行的情況它看不到，例如 Free 每日 10 萬請求用完回 1027、DNS 或帳號出問題。所以還要一個從外面打進來的探測。最小可行方案是：**UptimeRobot 免費版每 5 分鐘打兩個網址＋Workers Issues 推 Discord＋Cloudflare 事故通知**，費用 0 元，設定約 2 小時。GitHub Actions 排程 curl 只適合當第二道防線，因為它最短 5 分鐘、會延遲、會被丟掉，60 天沒活動還會被停用。

```
            ┌─────────── 外部 ───────────┐        ┌──────── Cloudflare 內部 ────────┐
 UptimeRobot ──每 5 分鐘──► /  與 /api/health   Worker 例外／5xx ──► Issues ──► Discord webhook
    │                       （站整個掛、1027、       Cloudflare 事故 ──► Incident Alerts ──► Email
    └─► Email／Discord        D1 額度用完）        （平台問題）
 GitHub Actions（選用）──每天──► 額度用量查詢 ──► 超過 70% 發 Discord
```

## Workers Logs 與 Metrics：Free 有，保留 3 天，但不會主動通知

**結論**：兩個 Worker 都已開 `observability`，出事後可以查最近 3 天的請求紀錄；指標可回看 3 個月。這些都是「事後查」的工具，不會主動通知。

**依據**：

- Workers Logs 的 Free 額度：每天 200,000 筆 log events、保留 3 天；Paid 是每月 2,000 萬筆、保留 7 天 ([Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/))。Free 超過每日上限後的行為（截斷還是取樣）**查不到**。
- 我們的用量：每次 `/api/*` 請求會執行前端與後端兩個 Worker，各寫 1 筆 invocation log（推論），所以 200,000 ÷ 2 = 100,000 次 API 請求。這剛好等於 Free 的每日請求上限 ([Workers Limits](https://developers.cloudflare.com/workers/platform/limits/))，log 額度不會比請求額度先用完（推論）。靜態檔不經過 Worker（`frontend/cloudflare.config.ts` 只有 `/api/*` 是 `runWorkerFirst`），請求也不計次 ([Workers Pricing](https://developers.cloudflare.com/workers/platform/pricing/))。
- 可以用 `head_sampling_rate` 降低取樣比例 ([Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/))，目前不需要。
- Metrics 可回看 3 個月，每次最多一週；invocation status 會區分 `exceededCpu` 等錯誤 ([Metrics and analytics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/))。
- Tail Workers：「available to all customers on the Workers Paid and Enterprise tiers」，Free 不能用 ([Tail Workers](https://developers.cloudflare.com/workers/observability/logs/tail-workers/))。

## Workers Issues：Free 唯一能「Worker 出錯就通知」的原生功能

**結論**：要開。它把未處理的例外、失敗的 invocation、5xx 回應、`console.error` 歸成 issue，再用 automation 推到 webhook，Discord 也支援。目前是 open beta、免費。限制是只有 Worker 有執行時才看得到。

**依據**：

- 偵測範圍：「When a Worker throws an uncaught exception, fails an invocation, returns a `5xx` response, or logs an error, Issues records the failure as an occurrence.」([Issues](https://developers.cloudflare.com/workers/observability/issues/))
- 費用：「Issues is available to all Workers accounts in open beta. It is free to use during the beta period.」([Issues](https://developers.cloudflare.com/workers/observability/issues/))。beta 結束後的價格**查不到**。
- 開法：`cloudflare.config.ts` 設 `worker.observability.issues.enabled = true` 再部署；文件有 `cf` 版本的範例。用 wrangler 部署的話要 4.134.0 以上 ([Issues](https://developers.cloudflare.com/workers/observability/issues/))。只處理開啟後的新流量。
- 通知：automation 的觸發有兩種，「Occurrence threshold」（次數跨過門檻時通知一次）與「Recurrence after inactivity」（沉寂一段時間後又出現）；目的地可以是 coding agent、generic webhook、chat、incident management。每帳號 50 個 automation ([Set up an automation](https://developers.cloudflare.com/workers/observability/issues/automations/))。
- Webhook 目的地「available on all plans」，沒有付費 zone 的帳號最多 100 個；內建 Discord、Slack、Google Chat 的格式 ([Configure webhooks](https://developers.cloudflare.com/notifications/get-started/configure-webhooks/))。
- 我們的程式在 D1 出錯時會丟出未處理的例外（`backend/src/index.ts` 沒有 try/catch），所以 Issues 抓得到；前端 Worker 只是 `env.API.fetch(req)`，後端回 5xx 時前端也會記一筆（推論）。

## Cloudflare Notifications：Free 能用的只有平台事故類

**結論**：Free 能開的是 Incident Alerts（Cloudflare 自己出事）、維護通知等，值得開，用來判斷「是我壞還是 Cloudflare 壞」。錯誤率、流量異常、用量告警都不能用。

**依據**：

- 錯誤率告警：Advanced Error Rate、Origin Error Rate、Traffic Anomalies 三種的「Included with」都是 Enterprise plans ([Available notifications](https://developers.cloudflare.com/notifications/notification-available/))；而且「Traffic alerts are configured per zone. It is not currently possible to configure alerts for a specific path or hostname.」([HTTP Traffic Alerts](https://developers.cloudflare.com/notifications/reference/traffic-alerts/))。`*.workers.dev` 不是我們的 zone，就算有 Enterprise 也套不上（推論）。
- 用量告警：Usage Based Billing 通知要 Professional 以上，而且只給 Pay-as-you-go 帳號 ([Available notifications](https://developers.cloudflare.com/notifications/notification-available/))。所以 Free 撞到每日 10 萬請求或 D1 額度時，**沒有任何原生通知**。
- 所有方案都有：Incident Alerts（可依影響程度與元件篩選）、Maintenance Notification、HTTP DDoS Attack Alert ([Available notifications](https://developers.cloudflare.com/notifications/notification-available/))。
- 「Workers 錯誤率告警」作為 Notifications 的類型：通知清單裡沒有 Workers 類別，**查不到**這種告警；最接近的是上一節的 Issues。

## Cloudflare Health Checks：要付費，也要 zone

**結論**：不能用。

**依據**：Standalone Health Checks 的可用性表：Free「No」、檢查數 0；Pro 10 個、Business 50 個 ([Health Checks](https://developers.cloudflare.com/health-checks/))。它監控的是「origin servers」，設定在 zone 底下；這個功能已併入 Smart Shield ([Health Checks](https://developers.cloudflare.com/health-checks/))。我們沒有 origin、也沒有 zone，買了網域用 Free zone 仍是 0 個，要到 Pro 才有（推論，依可用性表）。

## 外部免費探測：UptimeRobot 最合適

**結論**：主探測用 UptimeRobot（50 個監控、5 分鐘、有關鍵字監控、允許商業用途）。Better Stack 免費版檢查較頻繁（3 分鐘），但只有 10 個監控，告警只有 Email 與 Slack。GitHub Actions 只當補充。

| | UptimeRobot Free | Better Stack Free | GitHub Actions 排程 curl |
|---|---|---|---|
| 監控數 | 50 | 10（與 heartbeat 共用） | 不限（每個 job 一次） |
| 最短間隔 | 5 分鐘 | 3 分鐘 | 5 分鐘，且常延遲 |
| 告警管道 | Email；SMS、語音要另購；「Only 5 integrations」 | Slack、Email | 自己寫（Discord webhook、job 失敗寄信） |
| 關鍵字檢查 | 有（Keyword monitor） | 查不到 | 自己寫 |
| 資料保留 | 3 個月 | 查不到 | 執行紀錄最多 90 天（公開 repo） |
| 狀態頁 | 1 個 | 1 個 | 無 |
| 限制 | 「Good for personal and commercial projects」 | — | 負載高時可能被丟掉；公開 repo 60 天沒活動自動停用 |
| 來源 | [UptimeRobot Pricing](https://uptimerobot.com/pricing/) | [Better Stack Pricing](https://betterstack.com/pricing)；[Check frequency](https://betterstack.com/docs/uptime/check-frequency/) | [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)；[Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) |

GitHub Actions 的細節：

- 「The shortest interval you can run scheduled workflows is once every 5 minutes.」([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule))
- 「The `schedule` event can be delayed during periods of high loads… High load times include the start of every hour. If the load is sufficiently high enough, some queued jobs may be dropped.」([同上](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule))
- 「In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days.」([同上](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule))；有第三方說明停用時不會寄任何通知 ([cronuru 指南](https://cronuru.com/guides/github-actions-scheduled-workflows))。
- 分鐘數：公開 repo 用標準 GitHub-hosted runner 免費、不扣額度 ([Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions))。每 5 分鐘一次就是 288 次／天，每次至少佔一個 runner 開機（推論），免費但很浪費，而且 GitHub 本身延遲就可能超過 5 分鐘。

探測對額度的成本（推論）：

- 打 `/`：靜態檔，不經 Worker，不算請求、不讀 D1。只能證明靜態站活著。
- 打 `GET /api/cases`：每 5 分鐘 1 次，一天 288 次請求；目前約 495 列（224 件案件＋271 筆回報），288 × 495 ≈ 14.3 萬 rows read／天，是 500 萬的 2.9%。案件越多越貴，而且回應約 48 KB。
- 加一條 `GET /api/health` 只做 `SELECT 1`：一天 288 次請求、rows read 接近 0，回應幾十 bytes。這要改 API 合約（`frontend/src/shared/api.ts` 不用動，但 ARCHITECTURE.md 的 API 表要加），依 CLAUDE.md 規定先開小 PR。

## 額度預警：只能自己查

**結論**：Free 撞到每日上限時，Workers 回 1027 錯誤頁、D1 回錯誤 ([Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)；[D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))，而且沒有原生通知（見上節）。外部探測打 `/api/health` 會在撞牆後 5 分鐘內發現；想提前知道，就每天用 GitHub Actions 查一次 GraphQL Analytics，超過 70% 時發 Discord。

**依據**：Worker 指標與 D1 用量都可以用 GraphQL 查 ([Metrics and analytics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/)；[D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/))。Free 帳號能不能用 GraphQL Analytics API 查這兩個資料集，文件沒有明講（推論：可以，dashboard 的圖就是用它畫的）。門檻算式：Workers 100,000 × 70% = 70,000 次／天；D1 rows read 5,000,000 × 70% = 350 萬／天；rows written 100,000 × 70% = 7 萬／天。

## 對桶緝犯的意義

**R4（沒有監控與告警）**：建議分三步，全部 0 元。

1. **外部探測（約 1 小時）**：UptimeRobot 開兩個 HTTP(S) 監控，都是 5 分鐘一次。一個打 `https://tongjifan.ccyisyourbestfriend.workers.dev/` 並檢查頁面含「桶緝犯」；另一個打 `/api/health`（還沒做之前先打 `/api/cases?status=open`）。告警送 Email，有整合額度的話加 Discord。這一步涵蓋 Worker 沒執行的情況：1027、帳號被停、DNS。
2. **Workers Issues＋事故通知（約 1 小時，含一次部署）**：兩個 `cloudflare.config.ts` 加 `observability.issues.enabled: true`，由 Jin 部署；在 dashboard 建一個 Discord webhook destination，設「Occurrence threshold = 5」與「Recurrence after inactivity = 1 天」兩個 automation。同時開 Incident Alerts，篩 Workers 與 D1 元件，寄 Email。
3. **額度預警（約半天，選用）**：GitHub Actions 每天查一次前一天的 Workers 請求數與 D1 rows read／written，超過 70% 就發 Discord；和 02 的備份 workflow 放在同一個 schedule。issue R2 的輪詢問題修好前，這一步最有價值：一個開著的管理端分頁一天就能讀掉約 2,100 萬 rows。

不建議：升級 Pro 只為了 Health Checks（每個 zone 每月要付費，而且要先有網域），或用 GitHub Actions 每 5 分鐘 curl 當主要探測（延遲、會被丟掉、60 天停用）。

**R7（外部依賴）**：OpenFreeMap 官網寫明「At the moment, I don't offer SLA guarantees or personalized support」([OpenFreeMap](https://openfreemap.org/))。UptimeRobot 有 50 個名額，可以多開一個監控打 OpenFreeMap 的 style JSON，地圖空白時就知道是上游問題（推論）。這只能讓 Jin 早點知道，不能讓地圖恢復；降級（例如地圖失敗時改顯示地址清單）是前端的工作，不在本篇範圍。Google Fonts 失敗只影響字型，不監控。

**R3（無驗證）、R5（無備份演練）**：Issues 會把 4xx 以外的異常都記錄下來，但濫用（大量合法的 `POST /api/reports`）回的是 200／201，**Issues 看不到**。濫用要靠額度預警（第 3 步）與 04 的限流。備份 workflow 失敗也要發同一個 Discord 頻道，讓所有告警只看一個地方。

| 項目 | 成本 | 一次性工作量 | 持續工作量 |
|---|---|---|---|
| UptimeRobot 兩個監控 | 0 元 | 1 小時 | 0 |
| `/api/health` 路由（API 合約 PR） | 0 元 | 1 小時 | 0 |
| Issues＋Discord＋事故通知 | 0 元（beta 期間） | 1 小時＋一次部署 | 看告警 |
| 額度預警 workflow | 0 元 | 0.5 天 | 每 60 天確認 workflow 沒被停用 |
